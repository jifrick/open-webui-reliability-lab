# P04 — Injected memory context is alphabetically clipped, including mid-entry cuts

## Candidate and current status

- **Replacement issue:** [open-webui/open-webui#30235](https://github.com/open-webui/open-webui/issues/30235)
- **Live state checked:** Open; created 2026-09-20, updated 2026-09-27. Checked 2026-10-01.
- **Reported scope:** When memory context exceeds `memories.context_char_limit`, `add_memory_context()` alphabetically sorts rendered entries and slices the combined context string. This can silently omit later-sorting entries and cut a retained entry mid-text.
- **Affected users:** Users who have context memories exceeding the configured prompt-character budget; which content reaches the model can depend on alphabetical ordering rather than relevance.
- **Prior P04 candidate:** [#31663](https://github.com/open-webui/open-webui/issues/31663), “no way to reopen the chat controls pane after closing it,” is no longer the candidate. It was **closed 2026-10-01** after a comment explained that the header Controls button reopens the pane, a Toggle Controls shortcut is available, and desktop visibility persists across reload. The report itself acknowledged its inspection of a minified bundle was uncertain. The replacement #30235 has a separate, source-verifiable behavior and remains open.

## Reproduction and verification

**Issue’s reported steps:**
1. Add context memories so `[Memory Neighborhood]` and/or `[Relevant Context]` exceed the configured `memories.context_char_limit` (default 2,000).
2. Send a message that triggers memory context.
3. Inspect the prompt and observe omitted or partially clipped entries; add/edit memory and repeat.

The issue reports an observed rendered section of 2,521 characters against a 2,000-character limit, with later alphabetical entries omitted and one cut after 79 of 459 characters. The reporter says it reproduces on the latest release and dev commit `043784c2d`.

**Function-level reproduction against current source:** Executed the actual `add_memory_context` function extracted from `backend/open_webui/utils/memory.py`. The harness supplied a user query, mocked retrieval with three context strings of 800 repeated characters each, empty stored user memories, and a 2,000-character context limit. Exact output:

```text
rendered context length: 2000
entry length: 800 prefix: - AAAAAAAAAA tail: AAAAAAAAAAAA
entry length: 800 prefix: - BBBBBBBBBB tail: BBBBBBBBBBBB
entry length: 373 prefix: - CCCCCCCCCC tail: CCCCCCCCCCCC
third entry truncated: True
```

This reproduces the slicing mechanism in the production function and confirms a mid-entry cut. It does **not** run a complete chat request, persistent database, real vector retrieval, or a relevance-score selection; retrieval results were deliberately mocked. The harness observed 373 characters for its third entry; that synthetic output is distinct from the reporter’s 79/459 example.

## Source and source-backed cause

At imported `main` (`8bd8b4fac5e059578ac0c74b3c18d11139f88b7d`):

- [`backend/open_webui/utils/memory.py`, `add_memory_context`](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/utils/memory.py#L290-L407) gathers user, neighborhood, and query-retrieved memories.
- Around [line 370](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/utils/memory.py#L360-L374), each section is sorted by `(memory.casefold(), memory)`.
- Around [lines 375–399](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/utils/memory.py#L375-L400), user entries and other context entries receive separate character limits, but each joined section is truncated using Python string slicing.

**Cause established from source:** Alphabetical sorting controls the order before truncation, and raw slicing applies the cap to rendered text rather than selecting whole entries. The code does not preserve a memory’s retrieval rank when ordering the section, and slicing can split a memory. This confirms the mechanism. The specific 2,521-character production example and its exact memory selection remain reporter evidence, not a separate real-database reproduction.

## Proposed solution

Apply the configured budget to complete memory entries rather than a joined string. Preserve query retrieval order/rank where the retrieval API provides it; if a score/order is unavailable, use a documented deterministic fallback. Keep user memories separate from context memories and define what happens when one entry alone exceeds the budget (skip with explicit diagnostic, or a deliberate per-entry truncation policy). Do not imply score-based relevance ranking unless the retrieval data actually supplies comparable scores.

## Acceptance criteria

- No context memory entry is silently cut at a character boundary.
- The context budget is respected, with the chosen policy for labels, separators, headers, and oversized entries documented and tested.
- When retrieval rank/score is available, selection honors that ordering; ties and missing scores are deterministic.
- User memories remain isolated under their own limit and are not mixed into the context-memory budget.
- The rendered system prompt contains exactly the selected complete entries and remains stable for equivalent inputs.

## Regression-test plan

- Unit-test `add_memory_context` with synthetic user/neighborhood/retrieved entries exceeding both limits; assert entry boundaries, section order, and configured budget.
- Cover relevant/retrieval ordering, deterministic ties/fallback, duplicate IDs, empty results, and a single entry larger than the budget.
- Verify user and context budgets independently and confirm old memory context is replaced rather than duplicated across repeated calls.
- Add an integration test asserting that the serialized chat request includes the selected complete entries; no persistent-data migration is assumed unless implementation requires one.

## Risks and dependencies

- The current retrieval result shape and whether it exposes usable, comparable distances/scores must be verified before promising score-based relevance.
- A complete-entry policy must account for rendered labels, section headers, and delimiters—not only raw memory bodies.
- Oversized single entries and memory neighborhoods need an explicit selection policy; changed selections can change model answers and prompt size.
- Preserve the separate user-memory limit and avoid accidental changes to the deterministic ordering behavior introduced for #28292.

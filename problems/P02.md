# P02 — Edited assistant reply text is not searchable

## Candidate and current status

- **Issue:** [open-webui/open-webui#31471](https://github.com/open-webui/open-webui/issues/31471)
- **Live state checked:** Open; created 2026-09-27, updated 2026-09-27. Checked 2026-10-01.
- **Reported scope:** After editing and saving an assistant reply, its displayed text survives reload but chat search no longer finds the chat by that text.
- **Affected users:** Users who edit replies and later search chat history by words in the edited response.

## Reproduction and verification

**Reported steps (from the issue):**
1. Ask a question such as “Name a fruit that is yellow.”
2. Edit the assistant reply to include a unique term such as `Pineapplezz`, then save.
3. Reload and verify the edited reply is still visible.
4. Search for `pineapplezz`; avoid using a term present in the chat title.

**Reported result:** The edited reply is visible after reload, but search returns no chat.

**Function-level reproduction against current source:** Extracted `chat_search_message_content_match_sql('sqlite', 'needle')` from `backend/open_webui/models/chats.py` and ran it against an in-memory SQLite `Chat` JSON fixture. The message had `output` containing `Pineapplezz` and an empty `content` field. Output:

```text
edited response output contains Pineapplezz; content is empty
search by Pineapplezz: []
same JSON with content populated: [('c1',)]
```

This verifies the search predicate’s behavior for that representation. It does **not** exercise the full edit-save-reload flow or a persistent Open WebUI database.

## Source and source-backed cause

At imported `main` (`8bd8b4fac5e059578ac0c74b3c18d11139f88b7d`):

- [`src/lib/components/chat/Messages.svelte`, `editMessage`](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/src/lib/components/chat/Messages.svelte#L318-L405) handles response edits. When updating structured `output`, it assigns the edited output and sets the parallel `content` property to an empty string (around lines 393–400).
- [`backend/open_webui/models/chats.py`, `chat_search_message_content_match_sql`](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/models/chats.py#L59-L105) searches message `content` in the stored chat history and, on PostgreSQL, the `chat_message` representation; it does not extract text from structured `output`.
- [`backend/open_webui/models/chats.py`, `get_chats_by_user_id_and_search_text`](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/models/chats.py#L1966-L2070) uses that predicate for phrase and term matches.
- [`src/lib/components/chat/Messages.svelte`, `updateChat`](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/src/lib/components/chat/Messages.svelte#L176-L193) persists the history and only copies returned `content` into local history when it is truthy.

**Cause established from source:** The edit path can store the final assistant text in structured output while making `content` empty, but chat search matches `content` rather than rendered output text. The source predicate therefore cannot find a term that exists only in `output`. The harness verifies this mechanism; it does not independently verify the reporter’s complete UI sequence.

## Proposed solution

Keep the searchable representation aligned with what the UI renders. Prefer making search extract/index text from structured output (including supported output-text parts) or reliably materializing that text into `content` when saving an edit. Define handling for reasoning/tool output so search does not unintentionally index hidden or non-user-facing content. Preserve legacy message and database-dialect behavior.

## Acceptance criteria

- Search finds a saved edited reply by unique visible text after reload.
- Search stops matching text removed by an edit, unless that text remains elsewhere in the chat.
- Unedited assistant replies, user messages, title matches, output variants, and phrase/term matching continue to work.
- SQLite and PostgreSQL produce equivalent expected results for supported text content.
- Hidden reasoning or non-display output is not newly exposed through search unless explicitly intended.

## Regression-test plan

- Backend unit tests for SQLite/PostgreSQL search predicates using legacy `content`, empty `content` plus structured output text, and multiple output blocks.
- API-level test for search after saving an assistant output edit and after removing a previously searchable term.
- Frontend test that an edit is persisted and survives reload without regressing rendered output.
- Include phrase and single-term search, title-only matches, and control cases for unedited messages.

## Risks and dependencies

- The output schema includes message, reasoning, tool, and other block types; only intended visible text should be searchable.
- PostgreSQL searches both a normalized message table and embedded history; any synchronization or fallback change must avoid stale duplicate representations.
- Existing chats may already have structured output with empty `content`; a save-time-only fix would not repair those records unless search handles them or a migration is added.

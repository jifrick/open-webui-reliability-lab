# P12 — Moving a chat into a folder changes its recency

- **Issue:** [open-webui/open-webui#30362](https://github.com/open-webui/open-webui/issues/30362)
- **Current status:** Open when checked 2026-10-01; updated 2026-09-22.
- **Affected users:** Users organizing older chats into folders who expect conversation activity order to remain meaningful.
- **Reported reproduction:** In v0.11.4, select an older conversation from the unsorted Chats list and move it into a folder without sending a message or otherwise editing it. The report says its modified/activity timestamp advances and it appears newer, with ordering dependent on the sequence of moves.
- **Observed / expected:** Reported observed result is recency changing after an organizational operation; expected behavior is to keep activity recency unchanged when folder membership changes. The issue asks whether recency should instead use latest-message time; product semantics need confirmation.
- **Independent reproduction:** The current production `Chats.update_chat_folder_id_by_id_and_user_id` method was invoked with a fake database session and a chat timestamp of `1750000000`. It returned the assigned folder with `updated_at=1790840122` and `last_read_at=1790840122`. This directly confirms the timestamp mutation in the production method, but does not exercise a persistent database or visual sidebar ordering.
- **Source locations:** `backend/open_webui/models/chats.py::Chats.update_chat_folder_id_by_id_and_user_id` assigns `folder_id`, sets `updated_at` and `last_read_at` to the current time, and clears `pinned`. Chat listing order uses `Chat.updated_at` in `chat_list_order` and list queries; `backend/open_webui/routers/chats.py::get_chat_list_by_folder_id` exposes that ordering to folder listings.
- **Root cause:** Folder membership mutation intentionally updates the same `Chat.updated_at` column used as the default recency sort key. Thus sorting cannot distinguish a new message from a folder move.
- **Linked PRs / duplicate check:** `gh pr list --state all --search 30362` returned no matching PR when checked. Related reports cited by the issue are #26451 (sidebar timestamp field), #27484 (archive/folder visibility and refresh), #30180 (stale sidebar state), and #29501 (message timestamp storage); they are adjacent but do not establish a fix for the folder-move timestamp mutation. The current source still updates the timestamp.
- **History / release check:** Upstream `main` is `8bd8b4fac5e059578ac0c74b3c18d11139f88b7d`; `dev` is `015dbc8619568ac077ec1d782661836a63691ba1` (checked 2026-10-01). The folder-update method's timestamp behavior is unchanged on dev. Latest official release is v0.11.4 (2026-09-21), the version in the report. No issue-specific commit or release fix was found.
- **Proposed solution:** Separate organizational modification time from activity time, or make the activity sort derive from the latest message timestamp. Preserve folder move's read/pin/archive behavior only according to an explicit product contract; do not simply stop all timestamp updates without checking consumers.
- **Acceptance criteria:** Moving a chat between folders or into/out of the unsorted list does not change its activity position or activity timestamp; sending/editing a message still updates activity recency; pinned, unread, archived, and paginated folder views remain consistent.
- **Regression test:** Model/API test that captures timestamps/order before and after a folder move and verifies only folder membership changes. A separate message mutation test verifies activity recency still advances. Add UI coverage for ordering in unsorted and folder lists.
- **Risks:** `updated_at` may also be used for unread status, sorting, sync, or modified-time display; changing its semantics could affect other workflows. Latest-message timestamp may not exist for empty/imported chats.
- **Dependencies:** Product agreement on “recency” semantics, chat message timestamp availability, and consumers of `updated_at`/`last_read_at`.

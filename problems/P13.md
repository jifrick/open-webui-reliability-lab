# P13 — Memory context may change the prompt-cache prefix

- **Issue:** [open-webui/open-webui#30239](https://github.com/open-webui/open-webui/issues/30239)
- **Current status:** Open when checked 2026-10-01; updated 2026-09-20. This is an enhancement request, not a confirmed defect.
- **Affected users:** Users relying on provider or inference-server prompt/KV caching while memory context is enabled, especially with agentic memory writes.
- **Reported reproduction:** The issue describes enabling agentic memory plus system-context injection, allowing a memory tool to write during one response, then comparing the next provider request. It also notes retrieval is rebuilt from the last seven user turns even without a write, so the injected set can shift. The reported symptom is a changed system-message prefix and provider prompt-cache invalidation; the issue does not provide measured cache-hit telemetry.
- **Observed / expected:** The report seeks a cached/stably positioned memory block that changes only when its rendered content must change. Fresh memory updates still need to become visible; whether changed memory content should invalidate subsequent prompt tokens is an expected consequence that the requested optimization must explicitly account for.
- **Independent reproduction:** A function-level reproduction called current `add_memory_context` three times with patched retrieval/configuration adapters. With identical user input and identical retrieved memory, the resulting system-prompt bytes were identical (`same_retrieval_prompt_identical=True`; an unchanged rewrite did not change bytes). After changing the retrieved memory text, the prompt changed (`memory_update_changes_prompt=True`). This verifies current prompt construction behavior but does not measure real vector-retrieval drift, provider KV/prompt-cache hits, or latency.
- **Source locations:** `backend/open_webui/utils/middleware.py` calls `add_memory_context` during eligible chat payload processing (around line 2698) and executes function-calling tools in the same request flow (around line 5981); memory tools are implemented in `backend/open_webui/tools/builtin.py`. `backend/open_webui/utils/memory.py::add_memory_context` (around lines 290–406) builds the retrieval query from the last seven user messages, queries memory each request, sorts sections, removes any existing `<memory_context>` block, and appends the newly rendered block to the system message. `review_memory_after_turn` is a separate post-turn path.
- **Root cause:** There is no per-conversation rendered-context cache; memory retrieval/rendering runs each request and the prompt is reconstructed from current query/results. Source and the function-level test show reconstruction alone does not change bytes when content is identical; cache-prefix changes occur when the rendered memory content changes. That may reflect necessary freshness, retrieval membership drift, or other upstream prompt changes, and the claimed token-cost impact has not been measured in this lab.
- **Linked PRs / duplicate check:** No matching PR was found for #30239 when checked. The issue distinguishes #28292/#28293 (ordering instability) and related reports #30227 and #19169. #28292 is closed; its PR #28293 is marked closed without a merge timestamp, but a repository contributor commented “Addressed in dev.” Current `main` and `dev` both alphabetically sort memory sections with `casefold()` and a stable tie-break, so the original nondeterministic-order defect is not this candidate and should not be reintroduced.
- **History / release check:** Upstream `main` is `8bd8b4fac5e059578ac0c74b3c18d11139f88b7d`; `dev` is `015dbc8619568ac077ec1d782661836a63691ba1` (checked 2026-10-01). The memory rendering logic relevant to #30239 is the same on both branches. Latest official release is v0.11.4 (2026-09-21). No issue-specific upstream commit or release change addressing per-conversation caching was found.
- **Proposed solution:** First benchmark actual supported provider/cache behavior with unchanged and changed memory sets. If recomputation cost is measurable, cache retrieval/rendering by conversation, user, query/retrieval inputs, and memory revision; preserve stable block placement and invalidate only when relevant inputs change. Never keep stale memory solely to preserve a cache prefix.
- **Acceptance criteria:** With stable user/query/retrieval inputs, the serialized memory block remains byte-identical across turns; a memory update or relevant retrieval change becomes visible according to a documented freshness policy; one user's cached block cannot be reused for another; cache metrics show a measurable benefit on a supported provider.
- **Regression test:** Unit tests for identical-input stability and invalidation after add/update/delete; isolation tests across users/conversations; provider-mock tests that compare serialized request prefixes and record cacheable-prefix changes. A benchmark must compare real provider/cache telemetry before and after.
- **Risks:** Stale or cross-user memory, cache-key invalidation errors, added storage/state complexity, provider-specific cache semantics, and changing prompt freshness. A changed prompt cannot be guaranteed to reuse a cache beyond the unchanged prefix.
- **Dependencies:** A defined freshness contract, available memory revision/query identity, provider-specific cache metrics, and maintainer agreement that caching/retrieval cost warrants persistent or in-memory state.
- **Readiness:** Research candidate only. The source mechanism is verified, but no provider-level cost or cache-miss reproduction was performed; implementation should not proceed until the performance claim and freshness policy are validated.

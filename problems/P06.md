# P06 — Knowledge mutations return the full file listing

- **Issue/status:** [#31397](https://github.com/open-webui/open-webui/issues/31397), open, label `bug`; created 2026-09-25, updated 2026-09-27 (checked 2026-10-01).
- **Affected users / impact:** API clients that add, update, or remove files in large knowledge bases, especially bulk-ingestion clients. Each successful mutation can cause the server to query, construct, serialize, and return metadata for all linked files, even when the client needs only the mutation result.
- **Issue reproduction (reporter steps):** Create a knowledge base; repeatedly upload batches of 100 small text files and attach them through `POST /api/v1/knowledge/{id}/files/batch/add`; record each response duration, byte size, and `files` count. The reporter measured ingestion of 73,743 files and reported per-10,000-file rates falling from 9.1 to 6.9 documents/s, with 70,000 metadata entries in late responses. Those timings and scale measurements are reporter-provided, not independently reproduced here.
- **Source-backed behavior:** At upstream `main` `8bd8b4f` and `dev` `015dbc8`, `backend/open_webui/routers/knowledge.py` returns `Knowledges.get_file_metadatas_by_id(...)` after single add (route starts near line 1426), update (1525), remove (1614), and batch add (2037; including no-op and warning paths). `backend/open_webui/models/knowledge.py:651-675` selects metadata columns rather than `File.data`, but selects and materializes every row joined to that knowledge ID. The response model, `KnowledgeFilesResponse`, includes a list of `FileMetadataResponse` objects (`routers/knowledge.py:1094-1096`).
- **Direct reproduction / limits:** Called the actual single-add route function with mocked knowledge/file/vector persistence and a five-record metadata result. Exact output: `single add response files: 5 ['f0', 'f1', 'f2', 'f3', 'f4']`. This verifies that the route returns the full listing result; it does not measure SQL execution, HTTP serialization, or collection-size scaling. No live API or large database test was run.
- **Source-backed root cause (distinct from report):** Write routes build their response by invoking the all-files metadata query after mutation; there is no bounded mutation response in this path. Since the query excludes the extracted content column, this issue is not the full-content GET-listing problem; the remaining cost grows with the number of attached metadata rows.
- **Linked work / equivalent-fix check:** No PR matching #31397 was found. The issue discusses [#26144](https://github.com/open-webui/open-webui/issues/26144), [#17998](https://github.com/open-webui/open-webui/issues/17998), and [#12077](https://github.com/open-webui/open-webui/issues/12077). #26144 was a GET/list payload containing extracted content; it was closed after metadata-only listing work in [commit `46c1d659`](https://github.com/open-webui/open-webui/commit/46c1d6591badb6ab567ba1b8fae23475d5da105a). Its behavior is distinct, and the current POST response still returns all metadata rows. #17998 is broader collection-scale performance; #12077 is a closed, broad feature request, not this mutation contract. These were not identified as equivalent fixes.
- **Main/dev and release history:** Reviewed relevant router/model files at `8bd8b4f` (imported `main`) against `015dbc8` (upstream `dev` current 2026-10-01): identical for this behavior. No later v0.11.4 release exists in the checked release list; v0.11.4 was released 2026-09-21, before the issue. No matching entry for #31397 or this mutation-response behavior appeared in the inspected changelog.
- **Proposed solution:** Return a bounded mutation result (changed file metadata, counts, and warnings as needed); alternatively make the full listing explicit opt-in if API compatibility requires preserving the existing response. Confirm client/API expectations before changing the contract.
- **Acceptance criteria:** Successful add/update/remove responses do not query/serialize the entire collection by default; batch response cost is bounded by the batch and errors/warnings remain actionable; UI refresh still displays current membership; any compatibility mode is documented and tested.
- **Regression plan:** Route/API contract tests for single and batch add, update, remove, duplicate/no-op batch, partial failures, and warning payloads. Verify DB query does not enumerate unrelated existing files on the bounded path. Measure response item count/bytes at small and large collection sizes; add frontend test that refreshes the listing after mutation.
- **Risks / dependencies:** External API clients may rely on the existing `files` array; batch partial-success semantics and callers must be audited. Metadata can itself be large, but is not the content-blob behavior addressed by #26144.

# P08 — Regular auto-playback waits for generation to finish

- **Issue/status:** [#30422](https://github.com/open-webui/open-webui/issues/30422), open, label `enhancement`; created 2026-09-23, updated 2026-09-26 (checked 2026-10-01). A maintainer initially clarified existing behavior, then accepted the clarified request as a feature; it is not presented as a regression.
- **Affected users / impact:** Users who enable Auto-Playback Response and want spoken output during a long generated answer rather than after completion. Call-mode users already have a different streaming experience.
- **Concrete reproduction (issue steps):** Enable TTS/audio and Response Splitting (punctuation); enable Auto-Playback Response; request roughly half a page of text. Observe when `/speech` requests or browser speech begin relative to the answer stream. The issue reports requests begin after the full answer. Compare with call mode. Exact provider, generated text, and timing are not included in the issue.
- **Source-backed behavior:** At dev `015dbc8`, `src/lib/components/chat/Chat.svelte:2929-2935` triggers the normal auto-playback speak button only in the `done` branch. `ResponseMessage.svelte` then splits the completed content with `getMessageContentParts()` (around line 301) and sends those chunks to the TTS engine sequentially. In contrast, `Chat.svelte:1964-2000` dispatches complete chunks during streaming only when the call overlay is active. `CallOverlay.svelte:636-653` receives those chunks and fetches audio. This confirms the two different orchestration paths in source.
- **Direct reproduction / limits:** Static trace of the actual event path confirms that regular auto-playback starts in the completion branch while call overlay dispatches chunks from streaming updates. I did not run a browser, audio provider, or network-level `/speech` test; no measured latency or actual sound output is verified here.
- **Source-backed root cause (distinct from report):** The regular auto-playback setting invokes the existing “speak this completed message” UI action at completion; only call mode is wired to incremental chat events and sentence buffering. Response Splitting controls chunks passed to TTS after the speak action starts; it does not itself schedule requests during generation.
- **Related work / duplicate check:** Maintainer comments on #30422 explicitly distinguish the feature from Response Splitting and explain call mode’s current streaming path. The issue cites [#5894](https://github.com/open-webui/open-webui/issues/5894), an older open request about OpenAI’s real-time API; it is adjacent but not an equivalent normal-TTS auto-playback fix. Searches for PRs phrased around auto-playback sentence streaming found no matching change. Dev’s reviewed changes to Chat/ResponseMessage include nearby unrelated audio error handling but do not add this feature.
- **Main/dev and release history:** Imported `main` `8bd8b4f` and dev `015dbc8` both trigger regular auto-playback only on completion; reviewed source diffs did not reveal a candidate fix. v0.11.4 was released 2026-09-21, before the report; no later release or changelog entry for sentence-streaming auto-playback was found.
- **Proposed solution:** If maintainers want this UX, add a streaming auto-playback path that reuses sentence-boundary buffering and the audio queue without simulating a click on the final complete-message speaker. Preserve current completed-message behavior as the default or behind a clearly described option until UX is decided.
- **Acceptance criteria:** With streaming enabled, send each completed sentence to TTS before model completion; keep chunks ordered, flush a nonempty final remainder exactly once, and stop promptly on cancellation, chat switch, provider failure, or user stop. Disabled mode must retain current behavior. Non-streaming responses must still play correctly.
- **Regression plan:** Unit tests for punctuation/newline boundaries, short-chunk buffering, incomplete final sentence, empty output, cancellation/error, and streamed versus non-streamed responses; integration test with a delayed mock model stream and mocked TTS asserting the first request precedes completion. Add a browser test for queue order and cancellation.
- **Risks / dependencies:** TTS provider concurrency/rate limits, sentence segmentation across languages, playback queue races, duplicate audio between streaming and completion, interruption semantics, and a UX change for users who treat auto-playback as “read when finished.” The issue is a feature request; implementation scope requires product/maintainer agreement.

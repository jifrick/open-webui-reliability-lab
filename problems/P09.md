# P09 — Docling OCR when a document already has text

- **Issue/status:** [#31571](https://github.com/open-webui/open-webui/issues/31571), open, label `enhancement`; created 2026-09-29, updated 2026-09-29 (checked 2026-10-01). No issue comments were returned.
- **Affected users / impact:** Operators ingesting born-digital or externally OCRed PDFs through Docling, especially CPU-only Docling servers. If OCR is enabled by their Docling configuration, a second OCR pass could cost time and possibly introduce text differences. The external service’s exact defaults and OCR decisions are not controlled by Open WebUI source.
- **Concrete reproduction (issue report):** Configure `CONTENT_EXTRACTION_ENGINE=docling` and a Docling Serve endpoint; ingest a text-layer PDF with Docling OCR enabled, then compare extraction/OCR invocation with `do_ocr=false`; repeat with an image-only scan. The reporter describes a 23-page, 5.6 MB document: reported 846 s / 64,226 chars with `do_ocr:true` versus 85 s / 63,752 chars with `false`; they also report an image-only one-page control returning 0 text chars without OCR and 1,714 with OCR. These documents, configuration, timings, and outputs were **not independently available or verified**. The issue’s proposed per-document `pypdf` sampling code was not run.
- **Source-backed behavior:** At dev `015dbc8`, `backend/open_webui/retrieval/loaders/main.py:256-307` defines `DoclingLoader`; `load()` posts to `/v1/convert/file` and forwards `self.params` unchanged as form data. Loader construction at lines 633-639 passes `DOCLING_PARAMS` through. There is no source-level PDF text-layer detector or Open WebUI OCR-mode gate. Docling Serve receives the conversion request and determines how OCR parameters/defaults are applied.
- **Direct reproduction / limits:** Called the actual `DoclingLoader.load()` with a mocked successful HTTP response and `params={'do_ocr': True}`. Output: `calls: 1`; `endpoint: http://docling.invalid/v1/convert/file`; `do_ocr sent: True`; `documents returned: 1 'synthetic returned text'`. This verifies forwarding of an explicit setting only; it does not reproduce OCR, text-layer handling, extraction quality, or timings. No Docling server or test PDFs were available.
- **Source-backed root cause (distinct from report):** Open WebUI’s Docling adapter passes configured conversion params through but does not inspect document text or vary OCR per file. The issue’s more specific claim—that Docling re-OCRs text-layer pages based on bitmap coverage and that output cells can differ—is a claim about external Docling internals and was not independently verified against the deployed Docling version.
- **Related work / duplicate check:** No PR matching #31571 or “skip OCR” was found. Closed [#17025](https://github.com/open-webui/open-webui/issues/17025) requested text extraction plus OCR fallback and a `/v1` route; a maintainer commented “PR welcome” on 2025-08-31. Current source already uses `/v1/convert/file`, but no automatic text-layer/OCR selection. Open [#26947](https://github.com/open-webui/open-webui/pull/26947) reworks Docling’s synchronous loader into async submit/poll/retrieve with timeout; its stated scope does not implement OCR gating. The issue references #27987 for silent empty-content handling as a separate concern, not an equivalent fix.
- **Main/dev and release history:** The Docling OCR path at imported `main` `8bd8b4f` and dev `015dbc8` is materially the same: `/v1/convert/file`, params forwarded, no detector/gate. Dev has unrelated loader changes (including uploaded filename handling and text decoding); no candidate OCR fix was found. v0.11.4 was released 2026-09-21, before the issue; no later release or changelog entry for this candidate was identified.
- **Proposed solution:** First confirm Docling Serve’s supported OCR controls and the desired policy with maintainers. If implementing, add a conservative, opt-in `auto` decision for supported document types; skip OCR only on a reliable text-layer signal, preserve explicit `DOCLING_PARAMS` overrides, and log the decision. Do not claim per-page behavior unless the Docling API supports it.
- **Acceptance criteria:** With `auto`, confirmed text-layer PDFs avoid redundant OCR while retaining extracted text; image-only PDFs still receive OCR; mixed/empty/encrypted or unreadable PDFs follow a documented conservative policy. Explicit `do_ocr` settings retain precedence; default existing behavior remains unchanged unless intentionally versioned.
- **Regression plan:** Test born-digital, scanned, mixed-page, empty, malformed/encrypted, and externally OCRed PDF fixtures. Mock Docling requests to assert OCR flags per policy, then validate extraction and OCR invocation against supported Docling Serve versions. Measure cost only with reproducible fixtures and pinned service/model/runtime versions.
- **Risks / dependencies:** Heuristic false positives can suppress necessary OCR or false negatives can repeat expensive OCR; per-document sampling may miss scanned pages; Docling Serve versions/configuration vary; extraction correctness may regress. The issue’s performance and quality claims remain reporter measurements, not lab results.
